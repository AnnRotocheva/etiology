## 1. Контекст и назначение

### 1.1 Источник требований

Платформа автоматизирует зону ответственности (AoR) технической поддержки Keitaro:

- Управление критическими инцидентами (полная/частичная неработоспособность трекера)
- Глубокая техническая диагностика: сбор логов, окружения, воспроизводимых сценариев
- Формирование исчерпывающей технической спецификации для команды разработки — **ключевая заявленная ценность AoR**: не «жалоба», а тех.спецификация
- Incident Manager & Sync при массовых сбоях
- Обучение L1/L2 стандартам сбора диагностических данных

**Явно вне контура:** разработка/фиксы кода, управление релизами/деплойментом, поддержка кастомных решений клиента вне стандартного функционала.

**Ключевые метрики ценности:** Time to First Response; доля инцидентов, решённых без привлечения разработки.

### 1.2 Стратегическое позиционирование

Платформа спроектирована как **кросс-юнитовый сервис с самого начала**, а не как внутренний инструмент только для Keitaro:

- Keitaro — первый клиент/пилот, не единственный
- Проходит тест §6.2 стратегии Apliteni («могла бы функция быть отдельным SaaS?») — да
- Финансовая модель — internal invoice / shadow-pricing (§5.6), не бесплатная общая инфраструктура
- Владение (Lessly self-service слой vs отдельный service unit) — **открытый вопрос**, архитектура одинаково поддерживает оба варианта

### 1.3 Почему не готовое решение (build vs buy на уровне всей платформы)

На рынке существуют Slack-native AI-helpdesk продукты (ClearFeed, Unthread и аналоги), автоматически закрывающие до ~40% типовых Tier-1 обращений. Решение — **строить свою платформу**, обоснование:

| Требование | Закрывается готовым SaaS? |
|---|---|
| Каталог безопасных диагностических команд (серверная специфика) | Нет |
| MCP-native доступ для агентов других юнитов | Нет |
| Provider-independence (§7.5) | Нет — чужой AI-слой, чужой вендор-риск |
| Глубокая Keitaro-специфичная диагностика | Требует кастомизации до основания — экономия иллюзорна |
| Переиспользуемость как внутренний сервис компании | Нет — чужой SaaS никогда не станет активом Apliteni |

Текущее состояние в Lessly (email на дешёвых тарифах, Slack с человеком на дорогих) не содержит AI-автоматизации вообще — сам Slack без сторонних надстроек не умеет автономно решать обращения.

## 2. Архитектурные принципы

Базовые (заданы изначально): AI First, API First, MCP Native, Event Driven, Plugin Based, Modular, Extensible, Domain Driven Design, Separation of Concerns.

Добавлены по ходу проектирования:

- **Tenant Isolation** — сквозной принцип, обусловлен кросс-юнитовым позиционированием (п. 1.2)
- **Provider Independence** (§7.5 стратегии) — ни один AI-провайдер не должен быть единой точкой отказа; абстракция моделей обязательна
- **Privacy by Default** (§3.2) — персональные/чувствительные данные изолированы, никогда не используются для обучения моделей
- **Human-in-the-loop на необратимых решениях** — публикация в Knowledge Base, публикация post-mortem, команды вне каталога — везде черновик агента → утверждение человека, потому что ошибка тиражируется на всех клиентов, а не на одного

**Правило работы (зафиксировано пользователем):** не предлагать варианты/технологии, прямо противоречащие стратегии Apliteni, как жизнеспособные опции.

## 3. Верхнеуровневая архитектура

Пять слоёв, обёрнутых периметром безопасности и tenant isolation (кроме входного слоя каналов):

| Слой | Компоненты | Назначение |
|---|---|---|
| **Channels** | Chat widget, Slack, Email, API/MCP | Точки входа, вне периметра tenant isolation |
| **Domain layer (Support Operations)** | Diagnostics, Knowledge Base, Escalation & sync | Уникальное IP платформы — то, что нельзя взять «с полки» |
| **Agent layer** | Agent runtime, MCP gateway, Model abstraction | Исполнение и провайдер-независимость |
| **Platform core** | Event bus, Tenancy & identity, Observability, Approval Gate | Инфраструктурное ядро, переиспользуемое всеми доменами |
| **Data layer** | Event store, Domain context store, PII store (изолировано) | Источник истины; PII физически отделён |

## 4. Доменный слой: агенты Diagnostics

Три агента с жёсткими непересекающимися границами (правило: не допускать дублирования функций между агентами).

### 4.1 Triage Agent

| Параметр | Значение |
|---|---|
| Ответственность | Классификация обращения: severity, topic-тег, можно ли закрыть по Knowledge Base сразу |
| Границы | Не диагностирует технически, не пишет тех.спецификацию |
| Интерфейс | Вход: сырое сообщение клиента → Выход: событие `incident.triaged` |
| Модель | Быстрая/дешёвая (высокий объём, низкая сложность рассуждения) |
| MCP-инструменты | `knowledge_base.search`, `incident.create` |
| Права доступа | Read: Knowledge Base. Write: только создание записи инцидента |

### 4.2 Diagnostic Collector Agent

| Параметр | Значение |
|---|---|
| Ответственность | Сбор логов/окружения/repro steps; попытка само-закрытия по Knowledge Base; UI-гайдинг (куда нажать в трекере, включая аннотированные скриншоты из Knowledge Base); серверная диагностика через клиент-исполняемые команды из каталога |
| Границы | Не решает, эскалировать ли в разработку. Не пишет код, не деплоит. **Не имеет и не будет иметь инструмента для выполнения команд на инфраструктуре клиента ни в каком виде.** Не советует команды вне каталога — при отсутствии совпадения эскалирует на человека, а не генерирует команду свободно |
| Интерфейс | Вход: `incident.triaged` → Выход: `incident.resolved` либо `incident.needs_bug_report` |
| Контекст | Переписка по инциденту, логи/окружение клиента, лицензионные данные через External Context Provider |
| Модель | Средняя мощность |
| MCP-инструменты | `knowledge_base.search`, `license.get_status`, `customer.request_logs`, `catalog.get_diagnostic_command`, `docs.get_ui_screenshot` |
| Права доступа | Read: Knowledge Base, license data (не PII), история клиента. Write: обновление/закрытие инцидента |

### 4.3 Bug Report Composer Agent

| Параметр | Значение |
|---|---|
| Ответственность | Превращение диагностического контекста в исчерпывающую тех.спецификацию для инженеров Keitaro — ключевая заявленная ценность AoR |
| Границы | Не собирает данные заново, не пишет фиксы, не управляет релизами |
| Интерфейс | Вход: `incident.needs_bug_report` → Выход: `bug_report.created` |
| Модель | Сильнейшая в контуре — качество спецификации напрямую определяет скорость фикса |
| MCP-инструменты | `bugtracker.create_report`, `incident.link_report` |
| Права доступа | Read: весь диагностический трейл инцидента. Write: только создание bug-репорта |

### 4.4 Command Safety Gate (политика, не отдельный сервис)

Агент не оценивает опасность команды самостоятельно (ненадёжная точка отказа LLM). Вместо этого — выбор строго из провалидированного каталога:

```
Клиент запрашивает помощь
        ↓
Diagnostic Collector проверяет каталог команд
        ↓
   ┌────┴────┐
Найдено   Не найдено
   ↓           ↓
Команда    Эскалация
клиенту    на человека
(read-only,  (без генерации
клиент      новой команды)
исполняет
сам)
```

Каталог — курируемый актив с владельцем (аналогично Knowledge Base), пополняется только вручную. Это единственное жёсткое исключение из общего правила «Curator предлагает, человек утверждает» — сюда Curator Agent не имеет доступа вовсе.

## 5. Knowledge Base (актив, не агент)

| Тип контента | Источник наполнения | Версионируется по |
|---|---|---|
| Известные проблемы и решения | Ручное + предложения Curator Agent | Версия продукта/UI |
| Каталог диагностических команд | Только вручную | Версия окружения |
| Библиотека аннотированных скриншотов | Только вручную (решено: реальные скриншоты, не генеративные — надёжность важнее) | Версия UI Keitaro |
| Стандарты сбора данных для L1/L2 | Только вручную | — |

### Knowledge Curator Agent

| Параметр | Значение |
|---|---|
| Ответственность | Анализ закрытых инцидентов, поиск паттернов без записи в KB, формирование предложения |
| Границы | Не публикует в KB напрямую. Не имеет доступа к каталогу команд |
| Интерфейс | Вход: `bug_report.created`, `incident.resolved` → Выход: `kb_suggestion.created` (через Approval Gate) |
| Права доступа | Read: KB, Event Store. Write: только очередь предложений |

## 6. Escalation & Sync

### 6.1 Incident Coordination Agent

| Параметр | Значение |
|---|---|
| Ответственность | Обнаружение, что несколько инцидентов — один сбой (корреляция по времени/теме); master-инцидент; публикация статуса |
| Границы | Не диагностирует причину сама, не решает, чинить ли |
| Права доступа | Read: **все** активные инциденты (осознанное исключение из принципа минимального доступа). Write: только merge и статус |

### 6.2 Post-mortem Agent

| Параметр | Значение |
|---|---|
| Ответственность | По закрытию критического инцидента — сбор таймлайна/гипотез/причины/импакта в формат post-mortem |
| Границы | Не публикует сама — только черновик, публикация через Approval Gate в keitaro-internal-updates |
| Модель | Сильная — качество текста влияет на доверие команды к разбору |

## 7. Аналитика и CSAT

Реализуется как read-model поверх Event Store, без изменения ядра:

- **Feedback capture** — часть Escalation & sync, триггерит CSAT-опрос через существующие каналы доставки
- **Analytics & reporting** — проекции: тренды, топ-темы, CSAT, TTFR
- **Обязательное требование к схеме событий с самого начала:** каждое событие закрытия инцидента обязано нести topic/category-тег — иначе история до момента добавления классификации останется неразмеченной

Аналитика — внутри периметра tenant isolation: своя аналитика на юнит, не общий дашборд по всем клиентам.

## 8. Platform Core

### 8.1 Approval Gate (сквозной сервис)

Единый механизм «черновик → человек → публикация», переиспользуемый в KB, post-mortem и command-эскалации:

- Не содержит доменной логики — просто очередь pending-объектов + статус
- Технически: таблица в Postgres + уведомление через существующий канал (Slack)
- Каждый tenant видит только свою очередь

### 8.2 Event Bus

**Решение:** Postgres (LISTEN/NOTIFY + outbox) за абстрактным publish/subscribe интерфейсом.

Обоснование: тот же Postgres, что уже выбран под Event Store — не добавляем инфраструктуру, которую не тянет команда из одного человека. При росте нагрузки реализация за интерфейсом заменяется на Kafka/NATS без переписывания агентов.

### 8.3 Tenancy & Identity

**Решение:** Row-Level Security в Postgres (`tenant_id` на каждой строке) — не отдельная БД на юнит.

Второй уровень защиты помимо логики агентов: даже ошибка в коде агента не даёт прочитать чужие данные.

### 8.4 Observability

Дашборд поверх Event Store (сам Event Store — immutable audit log «бесплатно»). Build-or-buy: используем готовый BI-инструмент (Metabase/Grafana), не пишем свой UI с нуля.

## 9. MCP Gateway

Два независимых режима работы:

### 9.1 Server-режим (платформа отдаёт возможности наружу)

| Элемент | Решение |
|---|---|
| Реестр инструментов | Версионируемый список (`incident.create`, `knowledge_base.search`, `analytics.query` — ограниченный read/write) |
| Скоуп | Тот же tenant_id + права агента, что и внутри |
| Версионирование | Новая версия инструмента не ломает существующих потребителей молча |

### 9.2 Client-режим (платформа потребляет внешние MCP)

| Элемент | Решение |
|---|---|
| Реестр внешних серверов | Per-tenant список подключений (лицензиар Keitaro, strategy.apli.tech и др.) |
| Хранение секретов | Готовый secrets manager (Vault/облачный KMS) — **buy**, не собственная реализация |
| Деградация | Единый circuit breaker для всех внешних MCP — если источник недоступен, диагностика продолжается с пометкой «данные недоступны», не блокируется |

### 9.3 Build-решение

Строим поверх официального MCP SDK (протокол — готовый, tenant-scoping/реестр/circuit breaker — свои). Обоснование: MCP-native доступ — прямое конкурентное отличие от существующих решений на рынке (§3.1 — критичное и дифференцирующее строим сами).

## 10. Технологический стек (сводно)

| Компонент | Решение | Обоснование |
|---|---|---|
| Event Store | Postgres | Одна система вместо нескольких; команда из одного человека тянет самостоятельно |
| Agent runtime | LangGraph (или аналог) поверх собственного Model Gateway | §7.5 — provider independence, минимум два AI-провайдера + open-weights fallback |
| Event Bus | Postgres LISTEN/NOTIFY + outbox за абстрактным интерфейсом | Не плодим инфраструктуру раньше реальной нагрузки |
| Tenancy | Row-Level Security в Postgres | Дешевле отдельных БД на юнит, второй уровень защиты |
| Secrets | Managed vault (не своя реализация) | Безопасность — не зона конкурентного преимущества |
| Observability | Готовый BI (Metabase/Grafana) | Build-or-buy: строим только уникальное |
| Хостинг | Lessly — деплой через её MCP (staging/production, rollback, env vars) поверх обычного Docker-контейнера | Явное решение владельца проекта, заменяет прежний план на внешний PaaS. Приложение остаётся стандартным Docker-контейнером, в коде нет проприетарных фич Lessly — переносимость и provider independence на уровне хостинга сохраняются тем же способом, что и раньше |

## 11. Открытые вопросы (требуют решения до/во время реализации)

1. **Владение платформой:** Lessly self-service слой или отдельный service unit — влияет на DRI, P&L, shadow-pricing (§5.6). **Не путать с §10** — Lessly как хостинг/деплой-таргет уже решена; это отдельный организационный вопрос о владении самой платформой
2. **Классификация лицензионных данных:** содержат ли ответы лицензиара что-либо похожее на персональные/платёжные данные клиента — определяет, попадает ли этот коннектор под privacy-контур (§3.2)
3. Пороговые эвристики Incident Coordination Agent («что считать одним инцидентом») — определяются DRI по мере накопления данных

---

## 12. Явно вне архитектуры (границы платформы)

Наследуется из AoR — платформа не проектируется для:

- Написания или деплоя фиксов кода
- Управления релизами
- Поддержки кастомных решений клиента вне стандартного функционала
- Выполнения любых команд на инфраструктуре клиента (только advisory — клиент исполняет сам)
