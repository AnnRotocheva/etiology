# Design: MCP Gateway — server-режим (v1)

**Дата:** 2026-08-04
**Статус:** утверждён, готов к реализации (решения по реализации приняты автономно)

Ссылка на архитектуру: `docs/architecture.md` §9 (MCP Gateway), §9.1 (server-режим), §9.3
(build-решение).

## Контекст

Последний пункт из зафиксированной архитектуры. §9.3 явно требует: строить поверх официального
MCP SDK, не с нуля — «MCP-native доступ — прямое конкурентное отличие от существующих решений на
рынке, критичное и дифференцирующее строим сами» (§3.1). Client-режим (§9.2 — платформа
потребляет внешние MCP: лицензиар Keitaro, strategy.apli.tech) требует реальных внешних
серверов/секретов, которых нет — вне этого спека, тот же принцип, что и у остальных
незавершённых внешних интеграций сессии (Slack, bugtracker).

## Что уже проверено вручную перед проектированием

Официальный Python MCP SDK (`mcp`, PyPI) установлен и явно исследован (не угадан по памяти):
- `FastMCP` — сервер с декораторной регистрацией инструментов (`@server.tool()`).
- `FastMCP.call_tool(name, arguments) -> Sequence[ContentBlock]` — прямой вызов
  зарегистрированного инструмента **без сетевого транспорта** — то, что даёт возможность
  тестировать реестр инструментов из юнит-тестов, а не только через реальный stdio/HTTP-канал.
- Версия закреплена `mcp>=1.9,<2` — на PyPI уже есть `2.0.0`, но он свежий и непроверенный;
  `1.29.0` (последняя в ветке 1.x) стабильнее для прототипа.

## Решения

- **Только server-режим.** Client-режим (§9.2) требует реальных внешних MCP-серверов и
  secrets-хранилища (Vault/KMS — уже решено как buy, но самого хранилища в кодовой базе нет) —
  строить клиента подключаться некуда, тот же принцип «не строить недостроенное».
- **Ровно три инструмента, как зафиксировано в реестре §9.1** — не больше: `incident_create`
  (оборачивает уже существующий `triage()` — это буквально `incident.create` из MCP-инструментов
  Triage Agent, §4.1), `knowledge_base_search` (оборачивает `knowledge_base.search()`),
  `analytics_query` (оборачивает `top_topics()` + `resolution_rate()` из уже построенного
  read-model). Каждый — тонкая обёртка над уже существующей, уже протестированной функцией, без
  новой бизнес-логики.
- **Известное и явно задокументированное ограничение v1: `tenant_id` — открытый аргумент
  инструмента, не выведен из аутентификации вызывающей стороны.** Архитектура требует «Скоуп: тот
  же tenant_id + права агента, что и внутри» — то есть в проде это должно быть выведено из
  токена/API-ключа внешнего клиента, а не передаваться им самим. Полноценная реализация этого
  требует реальной системы аутентификации внешних клиентов + managed secrets vault для хранения
  их ключей — ни того ни другого в кодовой базе нет (secrets vault решён как buy, но не подключен
  ни к чему). Строить сейчас — то же самое переусложнение, что и с Slack/bugtracker: интеграция
  без того, с чем интегрироваться. v1 честно доказывает механику MCP-протокола и реестра
  инструментов; безопасная внешняя экспозиция — отдельная, более крупная задача (нужна
  auth-система), не тихая заглушка, а явно обозначенный пробел.
- **`build_server()` — фабрика, не глобальный singleton.** Принимает `gateway`/`publisher` и
  DI-параметры для нижележащих функций (тот же паттерн, что и во всех агентах сессии) — тесты
  подставляют фейки, реальная композиция (main.py/точка входа) — вне этого спека, поскольку живой
  точки запуска сервера (entrypoint) в проекте ещё нет ни для чего.
- **Версионирование инструментов** (§9.1: «новая версия не ломает существующих потребителей
  молча») — принцип на будущее, нечего строить сейчас: пока есть только первая версия каждого
  инструмента.

## Компоненты (`platform_core/mcp_gateway`)

```python
def build_server(
    *,
    gateway: ModelGateway,
    publisher: EventPublisher,
    triage_fn: Callable = triage,
    kb_search: Callable = knowledge_base.search,
    top_topics_fn: Callable = top_topics,
    resolution_rate_fn: Callable = resolution_rate,
) -> FastMCP
```

Регистрирует три инструмента:
- `incident_create(tenant_id: str, raw_message: str) -> dict` — вызывает `triage_fn`, возвращает
  `{incident_id, severity, topic_tag, kb_closable, kb_article_id}`.
- `knowledge_base_search(tenant_id: str, query: str) -> dict` — вызывает `kb_search`, возвращает
  `{articles: [{id, title, topic_tag}, ...]}`.
- `analytics_query(tenant_id: str) -> dict` — вызывает `top_topics_fn` + `resolution_rate_fn`,
  возвращает `{top_topics: [...], resolution_rate: {...}}`.

Каждый инструмент — тонкая обёртка: парсинг результата в JSON-совместимый dict, никакой
бизнес-логики сверх уже существующих функций.

## Тестирование

Юнит-тесты через `FastMCP.call_tool(name, {...})` с фейковыми `triage_fn`/`kb_search`/
`top_topics_fn`/`resolution_rate_fn` (тот же DI-паттерн, что и в агентах) — без реального
транспорта, без сети. Ответ приходит как `TextContent` с JSON-строкой — тесты парсят её обратно.
Без реального API-вызова в этом спеке — инструменты сами уже протестированы в своих модулях;
здесь проверяется только корректность обёртки/сериализации.

## Коммит

Один коммит: `pyproject.toml` (новая зависимость) + сам gateway.
