**Дата:** 6 августа 2026

## 1. Назначение

Сейчас показ прототипа коллегам — это чтение сырого текста в терминале
(`scripts/demo.py`, `scripts/demo_mass_outage.py`). Нужен браузерный интерфейс поверх
той же самой доменной логики — не новый продукт, а витрина для демо: ввести обращение
клиента, увидеть шаги пайплайна (Triage → Diagnostic Collector → Bug Report Composer →
Knowledge Curator) по мере выполнения, посмотреть очередь Approval Gate и одобрить/
отклонить/опубликовать прямо там же, увидеть аналитику.

Явно вне контура: это НЕ новый "Channel" в смысле §3 architecture.md (тот слой — про
продакшн-точки входа для клиентов: chat widget, Slack и т.д., причём Slack теперь и вовсе
исключён из схемы работы). Это внутренний demo/dev-инструмент, не часть периметра
tenant isolation в проде — тем не менее использует ту же tenant-scoped логику, что и
остальной код, без обхода RLS.

## 2. Рассмотренные подходы

| Подход | Плюсы | Минусы |
|---|---|---|
| **Streamlit (выбрано)** | Один Python-файл, ноль JS/сборки, готовые виджеты (форма, спиннер, таблицы) — минимальный DevOps-оверхед, соответствует принципу компании | Не production-grade UI-фреймворк — но это и не нужно, это demo-инструмент |
| FastAPI + HTML-шаблоны | Полный контроль над версткой | В разы больше кода ради демо; нужен свой JS для "показывать шаги по мере выполнения" |
| Gradio | Тоже быстро | Меньше подходит под "несколько экранов" (пайплайн / очередь / аналитика), чем Streamlit с его multipage |

Streamlit — прямое соответствие принципу "бережные траты, минимальный DevOps-оверхед на
одного человека" (CLAUDE.md): новая dev-зависимость, ноль инфраструктуры, `streamlit run`.

## 3. Архитектура

Новый файл `scripts/demo_ui.py` (Streamlit-приложение), никакого нового пакета — это
demo-обвязка, а не доменный код. Импортирует и вызывает ровно те же функции, что уже
использует `scripts/demo.py`/`demo_mass_outage.py` (`triage`, `collect`, `compose`,
`curate`, `coordinate`, `ApprovalGate`, `publish_approved`, analytics) — без дублирования
бизнес-логики, без нового MCP-слоя (UI зовёт доменные функции напрямую, как demo.py, не
через MCP-протокол — MCP тут не даёт ничего, только сложность).

Streamlit — синхронный фреймворк, доменные функции — `async def`. Обёртка: один общий
`asyncio.run(...)` вызов на каждое действие пользователя (клик кнопки), без долгоживущего
event loop — то же самое, что уже делает `demo.py`.

Экраны (Streamlit multipage — файлы в `scripts/demo_ui_pages/`, диспетчер в `demo_ui.py`):

1. **Пайплайн** — текстовое поле для сообщения клиента, кнопка "Отправить". После отправки
   поэтапно (`st.status`/expander на каждый шаг) показываются: Triage → Diagnostic
   Collector → (если эскалация) Bug Report Composer → Knowledge Curator — то же дерево
   решений, что в `demo.py`, просто в UI вместо print().
2. **Approval Gate** — таблица pending-предложений по тенанту, кнопки Approve/Reject на
   каждой строке; для одобренных `kb_suggestion` — кнопка "Опубликовать" (`kb_publish_approved`).
3. **Массовый сбой** — кнопка "Запустить сценарий" воспроизводит `demo_mass_outage.py`
   (три захардкоженных сообщения) и показывает результат корреляции.
4. **Аналитика** — топ тем, resolution rate, CSAT summary (те же вызовы, что в конце `demo.py`).

Тенант фиксирован — `keitaro-demo` (как в CLI-скриптах), выбора тенанта в UI нет (не
production multi-tenant интерфейс).

## 4. Данные и состояние

Никакого нового состояния — всё читается/пишется через существующие доменные функции
и Postgres. `st.session_state` используется только для UI-эфемерности (что сейчас
отображено на экране), не для бизнес-данных.

## 5. Обработка ошибок

Переиспользуется та же идея, что уже добавлена в CLI-скрипты: если локальная БД не
поднята — понятное сообщение в UI ("Не удалось подключиться к БД — `bash
scripts/db_start.sh`"), не голый traceback.

## 6. Тестирование

Это demo-обвязка поверх уже протестированного доменного кода (85 тестов покрывают
`triage`/`collect`/`compose`/`curate`/`coordinate`/`ApprovalGate`/`publish_approved`) —
дублировать их через UI-тесты не нужно (YAGNI). Проверка — то же, что для CLI-скриптов:
живой прогон (`streamlit run scripts/demo_ui.py`), ручная проверка всех четырёх экранов.
Автотестов на сам UI-слой не пишем, как их нет и для `demo.py`/`demo_mass_outage.py`.

## 7. Зависимости

`streamlit` добавляется в pyproject.toml как отдельная extras-группа `demo` (не `dev` —
это не тест-тулинг, и не основная зависимость пакета `etiology` — прод-контейнер её не
тянет): `pip install -e ".[demo]"`.
